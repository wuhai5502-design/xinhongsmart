Android Firmware and Software Customisation for OEM Builds

Boot chain · App protection · Build identity · Branding removal · What to confirm before tooling

Home / News / Firmware Customisation

By Xinhong Smart Engineering Team · Published 27 November 2026 · 10 min read

Quick answer: firmware customisation is not one change but three separate ones, each with its own constraint. The boot chain decides what can be rebranded and whether the device still verifies itself; the app trust boundary decides whether your application can be removed and whether it survives a factory reset; and the build identity decides what the device calls itself while the regulatory record has to stay intact. Get the order right and the rest is packaging. Get it wrong and the first OTA undoes the project.

Where each customisation actually lives

A tender usually lists the desired outcomes - logo, wallpaper, app, model name - without saying where in the system each one sits. The location determines the effort and the risk.

What the buyer asks forWhere it is implementedWhat it can break
Boot logo and animationA logo partition or resource read by the bootloader, then bootanimation.zip in the system imageA logo written into a signed boot chain invalidates the signature unless the image is rebuilt and re-signed with the manufacturer's key
Default wallpaper, launcher, UISystem or product partition, settable from the image or by a device policy at provisioningPolicy-set defaults can be reset by the user unless the device is managed; image-set defaults survive a factory reset
Pre-installed applicationEither in the system image with platform privileges, or installed after first boot as a normal appA system app survives reset but must be updated by a mechanism that can write the system image; a normal app updates easily but the user can remove it
Device model name and build propertiesBuild properties compiled into the image, plus sometimes values read by the settings UIAnything the OTA updater uses to match a build must stay consistent, and the regulatory identifiers must remain in the production record even if the UI shows another name
Packaging and accessoriesOutside the software entirelyNothing technical; the constraint is lead time, not engineering

Two of those rows carry a warning that buyers rarely see in a quotation. The boot chain is verified: Android's verified boot computes a hash over the boot and system images and checks it against a signed descriptor. Changing the logo can change that hash. The manufacturer either rebuilds and re-signs the image with the key the device expects, or the device starts reporting a verification failure - which is why "can you change the boot logo" is really a question about signing keys, not graphic design.

Three ways to stop an application being uninstalled

This is the requirement that most often arrives as a single sentence and contains two different requirements: the app must not be removable by an ordinary user, and it must come back after a factory reset. Only one of the three common mechanisms satisfies both.

MechanismHow it worksSurvives factory resetTrade-off
System-privileged appThe APK is built into the system image and signed by the manufacturer, so the user has no uninstall pathYesEvery update needs a route that can write the image, or a privileged updater; the key has to be retained for the life of the fleet
Device owner (Android Enterprise)Your app is the device policy controller, provisioned at setup; a device owner can make itself non-removableNo - the reset clears ownershipNeeds a provisioning step (QR, zero-touch or an enrolment token) and a GMS build in most deployments
Kiosk or lock task modeThe device runs one application full-screen and the launcher is not reachableOnly if the mode is re-appliedStrongest on the screen, weakest on the package: it restricts the UI rather than the app's presence

The practical answer is usually a combination: the application built into the image so it cannot be removed and returns after a reset, kiosk mode so the operator sees only that application, and device owner if the fleet also needs remote policy. Asking for one mechanism to do all three is how projects end up with an app that is either removable or unupdatable.

Build identity against regulatory identity

Changing what the device calls itself is straightforward in the build, and it is where programmes get into trouble, because two different identities are involved.

The commercial identity - the model name in settings, the build fingerprint, the brand string - lives in build properties compiled into the image. A new name means a new image, and the update mechanism has to accept it as a legitimate build.

The regulatory identity - the model number on the certification documents, the radio approvals, the label on the housing or under the battery - is a legal record, not a string in a settings page. It has to survive in the production records and on the device label even when the commercial name changes. A tender that says "remove all manufacturer branding" and a regulator that expects a model identifier are both satisfied only when the label requirement is written down explicitly.

Branding removal: cosmetic against contractual

Removing the manufacturer's logo from the boot screen, wallpaper and interface is a software task. Three things are not.

  • Certification marks and identifiers. CE, FCC ID, the model number and any energy or radio marking are part of the product's compliance evidence. They can move, but they cannot disappear.
  • Licence notices. The open-source licences in the image carry attribution requirements, and some third-party components require a visible notice in the settings.
  • GMS requirements. A build carrying Google Mobile Services has display and attribution conditions of its own; a fully unbranded build is usually an AOSP build, and that changes what the device can run.

So the useful question is not "can you remove the branding" - it can be removed - but "which marks have to stay, and where". The answer decides whether the build is GMS or AOSP, and that decision comes before the image is compiled, not after.

The security list: what each item depends on

Institutional tenders arrive with a table of security features. The features are not independent: several depend on the same signing key or the same build type, so the answers have to be consistent.

Secure boot and verified bootBoth depend on the bootloader state and the signing keys. Ask who holds the key, whether the bootloader can be unlocked, and how a custom logo is re-signed
Firmware signingAsk how OTA packages are verified, which key signs them, and what happens to the fleet if that key is lost

Keeping the customisation alive through updates

The requirement that decides whether a programme survives year two is not the first image; it is the update path. Three questions settle it.

  1. Which parts of the build does an update replace? If the OTA writes the whole system partition, every future update has to carry your logo, wallpaper, launcher and system app. If it patches only some partitions, the customisation may survive - but only if the signing and versioning are arranged for it.
  2. Who signs the update? Your application's update must be signed with the key the installed version expects. If the system app is platform-signed and the update is signed with a different key, Android rejects it.
  3. What is the fallback? A documented path to re-flash a device that fails an update is worth more than a promise that updates never fail.

What a custom sample has to prove

Before a first order, a sample is the cheapest place to catch every one of these questions. A sample that only shows the logo is a packaging proof, not a firmware proof. The acceptance run should show:

  • the boot sequence, from power-on logo to launcher, on a device that has been factory reset;
  • the application present after the reset, and an attempt to uninstall it blocked;
  • the model name in settings, next to the label on the housing, with the regulatory identifier visible;
  • one real update applied to the custom build, without losing the customisation;
  • the security features that were promised, switched on, and the patch level reported in settings.

The Android OS customisation page covers the build choices - GMS or AOSP, version pinned to the platform, pre-installed applications and kiosk behaviour - and the software customisation page covers the module interfaces your application drives. Both are worth reading before the requirement list is written, because the answers change what can be promised.

Frequently Asked Questions

Can the boot logo and animation be replaced?
Yes, when the manufacturer controls the signing key for that build. The logo sits in the boot chain that verified boot checks, so the image has to be rebuilt and re-signed rather than edited. Ask for the accepted image dimensions and format, whether a static logo and an animated sequence are both supported, and who re-signs the image after the logo changes.
Can an app be made impossible for a user to uninstall?
Yes, by building it into the system image with platform privileges. That is the only mechanism that also survives a factory reset. Device-owner mode prevents removal during normal use but is cleared by a reset, and kiosk mode restricts the interface rather than the package. State both requirements - not removable and returns after reset - because only the system-app route satisfies both.
Does changing the device model name break certification?
It changes the commercial identity, not the certification record, provided the regulatory model number and label stay intact and the production records still trace to them. The practical risk is the update path: the updater must accept the new build fingerprint as a legitimate build, which is decided when the image is compiled.
Can all manufacturer branding be removed?
Cosmetic branding can be removed: boot logo, wallpaper, launcher labels and promotional applications. Certification marks, radio identifiers, open-source attribution and any GMS display requirements have to stay somewhere. A fully unbranded build is usually an AOSP build, which also removes Play services, so that decision comes before the image is built.
Does custom firmware invalidate GMS certification?
It can. GMS certification applies to a build that passed compatibility testing; changes to system properties, the boot chain or the pre-installed application set may take the build outside what was certified. If the deployment needs managed provisioning or Play services, confirm with the manufacturer that the custom build keeps GMS, and get that in writing.
How are customised devices updated in the field?
Either through the manufacturer's OTA channel, which delivers a complete custom image each time, or through your MDM for the application layer only. The first keeps the customisation consistent and puts the burden on the manufacturer; the second is faster for app changes but cannot alter the system image. Most programmes use both, with a written rule about which change goes through which channel.
